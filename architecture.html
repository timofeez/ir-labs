Архитектура#

Как устроены проекты: из каких частей состоят, как данные проходят от сайтов до результата поиска, какой файл за что отвечает. Построчный разбор кода — на странице Код построчно.

Общая схема: от сайтов до поиска#

  Википедия (ru, en)            газета «Гудок»
   API MediaWiki                  sitemap.xml + HTML
        │                              │
        ▼                              ▼

                            │                 ┌──── ЛР2: lab2 (Python) ─────┐

                            │                 └─────────────────────────────┘
                            ▼

 │ prepare.py ─► data/corpus.tsv                                           │
 │                   │                                                     │

Принцип: каждая следующая работа использует результат предыдущей. Корпус ЛР1 — вход для поисковой системы; правила токенизации (ЛР3) и стемминга (ЛР4) одни и те же в индексаторе, частотном анализе и поиске, потому что находятся в общих заголовочных файлах.

ЛР1 — сбор корпуса#

crawl.py                download_all.py              extract.py                corpus.py
BFS по категориям  ──►  тексты статей пачками  ──►   wikitext / HTML → текст   просмотр, статистика
*_titles.tsv            по 50 через API             *_text.jsonl
                        *_raw.jsonl                 corpus_stats.json
gudok.py: sitemap → HTML статей → gudok_raw.jsonl.gz ─────┘
Компонент Ответственность
crawl.py обход дерева категорий в ширину, список pageid статей
download_all.py скачивание вики-разметки, продолжение после обрыва
gudok.py список статей из карты сайта, скачивание HTML
extract.py очистка разметки, метаданные, статистика корпуса
corpus.py, lab1.exe консольный просмотр корпуса

Хранение — файлы JSONL (одна строка — один документ): их можно дописывать, и при обрыве скачивание продолжается с последней целой строки.

ЛР2 — поисковый робот и распределённая БД#

                       ┌───────────── robot.py ─────────────┐
 config.yaml ────────► │ seed → crawl_frontier → recrawl     │
                       │   │        │  allowed (robots.txt)  │
                       │   │        │  get (задержка, повтор)│
                       │   │        │  normalize_url         │
                       │   │        │  duplicate_of (хеш)    │
                       └───┼────────┼────────────────────────┘
                           ▼        ▼
                       db.py: connect_any (первый живой узел), reconnect
                           │  SQL (протокол PostgreSQL)
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
     узел 1 :26257     узел 2 :26258     узел 3 :26259
         └──── Raft: каждый диапазон в 3 копиях ────┘
     таблица documents — 5 диапазонов (шардов) по ключу url
     таблица frontier  — очередь URL, состояние обхода
Компонент Ответственность
Robot.seed стартовые категории / адреса из sitemap → очередь
Robot.crawl_frontier берёт следующий URL, скачивает, сохраняет, отмечает состояние
Robot.process_category достаёт из страницы категории подкатегории и статьи
Robot.recrawl проверка изменений: условный GET / lastmod, сравнение хеша
db.py создание базы и таблиц, подключение к живому узлу
start_cluster.bat запуск трёх узлов и инициализация кластера
lab2.exe утилита: кластер, статистика, демонстрация отказа узла

Ключевое решение — всё состояние в БД: очередь (frontier) и документы (documents). После каждой страницы делается commit, поэтому робот можно остановить в любой момент и продолжить. Распределённость: данные шардированы на диапазоны и реплицированы на 3 узла; падение одного узла не останавливает работу (большинство 2 из 3).

ЛР3–8 — поисковая система на C++#

Модули#

common.h ─── Vec<T>         динамический массив (вместо std::vector)
         ├── LineReader     быстрое чтение строк большого файла
         ├── utf8_decode / utf8_encode, char_class, to_lower
         ├── next_token     токенизатор  ◄── ЛР3
         ├── TermTable      хеш-таблица термов (FNV-1a, открытая адресация)
         └── формат index.bin: константы, rd16/rd32/rd64, cmp_bytes
stem.h  ──── stem::stem → stem_ru (Snowball) / stem_en (Портер)  ◄── ЛР4

tokenize.cpp  ─ common.h                  токены и статистика      (ЛР3)
stemtest.cpp  ─ common.h + stem.h         слово → основа           (ЛР4)
termfreq.cpp  ─ common.h + stem.h         частоты, ранги           (ЛР5)
indexer.cpp   ─ common.h + stem.h         корпус → index.bin       (ЛР7)
search.cpp    ─ common.h + stem.h         index.bin + запрос → документы (ЛР8)

                                  │
                                  ▼
                 next_token ─► TermTable.get_or_add ─► [stem::stem] ─► id терма

Конвейер поиска (ЛР8)#

запрос "электровоз (вл80 || чс2) !музей"
   │
   ▼ lex: токены; слово → next_token → [stem] → find_term (двоичный поиск)
TERM AND LP TERM OR TERM RP AND NOT TERM
   │
   ▼ Parser: рекурсивный спуск (or → and → unary)
        AND
       /    \
    AND      NOT
   /   \       \
 TERM   OR     TERM
       /  \
    TERM  TERM
   │
   ▼ eval: op_or / op_and / op_and_not над отсортированными списками
список документов ─► doc_info ─► заголовок + URL

Решение Почему
Без STL, свои Vec и TermTable требование лабораторных; полный контроль памяти
Общие common.h и stem.h одинаковая токенизация и стемминг при индексации и поиске
Свой бинарный формат индекс загружается одним чтением файла, без разбора
Отсортированные posting-листы И/ИЛИ/НЕ за линейное время методом двух указателей
Отсортированный словарь поиск терма двоичным поиском, O(log T)
Отдельный процесс search для веб-сервиса индекс загружается один раз, запросы идут через stdin/stdout
